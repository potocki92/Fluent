# Fluent

A German vocabulary learning app for Polish speakers. Learn by reading German
passages, taking adaptive comprehension tests (ability tracked with an Elo-style
rating), and reviewing vocabulary with SM-2 spaced-repetition flashcards.

## Tech Stack

- **Next.js 16** — App Router, TypeScript (`strict`), `src/`-rooted
- **Tailwind CSS v4** + **shadcn/ui** on `radix-ui` (dark theme, CSS-variable tokens)
- **Supabase** (`@supabase/supabase-js`, `@supabase/ssr`) — auth, Postgres, RLS
- **Zustand** — client-only ability state · **TanStack Query** — server-data fetching/caching
- **Recharts** — progress chart · **Framer Motion** — flashcard flips & transitions
- **lucide-react** icons
- **SM-2** spaced repetition + **Elo** ability estimation (pure, unit-tested, in `src/lib/`)

## What's in Supabase

The schema lives in [`supabase/schema.sql`](./supabase/schema.sql).

| Table         | What it holds |
| ------------- | ------------- |
| `words`       | DTZ dictionary (target: 2588 entries). Headwords — lemma, `display` ("die Autobahn"), article, `word_type`, gender — are factual linguistic data; the Polish translations, example sentences, and CEFR level are generated by Claude (see the import pipeline). |
| `texts`       | Reading passages (original, **not** from DTZ). `body` is HTML linking word lemmas via `<mark data-lemma="X">`; `difficulty` is the text's Elo rating. |
| `questions`   | Comprehension questions per text. `correct_idx` is **never** exposed to the client — it is read only inside the `submit-answer` server action. |
| `profiles`    | One per auth user: Elo `ability`, rating deviation `rd`, `answered` count, cached `cefr_estimate`, `streak_days`, and `level_source` (where the level came from). Auto-created on signup by a trigger. |
| `attempts`    | Immutable audit log — one row per answered question, recording `ability_before`/`ability_after` and the session it came from. |
| `test_sessions` · `test_session_items` | One graded reading test. The server snapshots which questions it is scored on; each item holds exactly one answer. See [Test session lifecycle](#test-session-lifecycle). |
| `calibration_sessions` · `calibration_session_items` | The same for the adaptive placement test, so its result can be replayed server-side. |
| `text_completions` | Per-learner, per-text result (latest wins) — drives the "read & passed" section. |
| `saved_words` | Bookmarked vocabulary with SM-2 SRS state (`interval`, `repetitions`, `ease_factor`, `due_at`, `is_mastered`). **Scheduling only** — what the learner knows lives in `user_word_knowledge`. |
| `skills` · `concepts` | Reference catalogs: the eight skill dimensions and the ~30 weakness concepts (`preposition_case`, `article_gender`, …), each with a Polish label. Public-read, admin-write. |
| `learning_events` | Append-only evidence log — one row per learning interaction (test answer, placement answer, review), never rewritten. See [Learning engine](#learning-engine). |
| `review_events` | Full spaced-repetition history: rating, mode, direction, and the SM-2 state **before and after** each graded card. |
| `user_skill_state` · `user_concept_state` · `user_word_knowledge` | Aggregated knowledge: an estimate plus, separately, how much evidence stands behind it. Derived from the event log; the app reads these, never the log. |

All tables have Row Level Security enabled. `words`/`texts` are public-read;
`questions`/`calibration_questions` are admin-only (learners read the answer-free
`*_public` views). Everything holding learner progress is **read-only to the
learner who owns it** — see [Who may write what](#who-may-write-what).

## Setup

1. **Clone** the repository.
2. **Install dependencies**: `npm install`.
3. **Create `.env.local`** (copy from [`.env.example`](./.env.example)):
   ```
   NEXT_PUBLIC_SUPABASE_URL=...
   NEXT_PUBLIC_SUPABASE_ANON_KEY=...
   SUPABASE_SERVICE_ROLE_KEY=...      # server-only, never prefix NEXT_PUBLIC
   ```
   All three are required at runtime. The service-role key is the learning
   engine's credential: finalizing a test writes progress through functions that
   are deliberately unreachable with the public anon key (see
   [Who may write what](#who-may-write-what)).
   In **Authentication → Providers** enable **Anonymous** and **Email (magic link)**.
4. **Run the schema**: paste [`supabase/schema.sql`](./supabase/schema.sql) into
   **Supabase Studio → SQL Editor** and run it. It is idempotent — safe on a fresh
   *or* an already-provisioned database. On a project that is already using the
   Supabase CLI, `supabase db push` applies
   [`supabase/migrations/`](./supabase/migrations/README.md) instead; the two
   describe the same database.
5. **Seed the demo texts**: `node import/seed-texts.mjs`
   (seeds the 3 demo texts — *Im Supermarkt* / *Beim Arzt* / *Umzug* — and their
   questions). Requires `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` in the environment.
6. **Import the dictionary**: `node import/translate-import.mjs`
   (translates the DTZ wordlist into Polish with example sentences via Claude;
   requires `ANTHROPIC_API_KEY`, costs ~$3 one-time for the full list). Runs in
   batches and is safe to re-run — already-translated rows are skipped.
   ```bash
   export SUPABASE_URL=...
   export SUPABASE_SERVICE_KEY=...
   export ANTHROPIC_API_KEY=...
   node import/translate-import.mjs [--start 0] [--batch 50] [--dry-run]
   ```
   > **Note:** `import/dtz_words_seed.json` in this repo is a small representative
   > sample (~20 words) so the pipeline is runnable end-to-end. Supply the full
   > 2588-row DTZ headword list (same shape) to import the complete dictionary.
7. **Run the dev server**: `npm run dev`, then open http://localhost:3000
   (the root redirects to `/learn`). Routes: `/learn`, `/review`, `/browse`, `/stats`.

## Test session lifecycle

A comprehension test is not a list of questions the browser posts back — it is a
**session the server owns**, from the first question to the immutable result.

```
startTestSession(textId)
        │  the SERVER picks the questions and snapshots them
        ▼
test_sessions (in_progress) + test_session_items — one row per question
        │
        ▼
answerTestQuestion(sessionId, questionId, selectedIdx)     ← once per question
        │  writes the answer, THEN reveals that question's key
        ▼
every item answered
        │
        ▼
finalizeTestSession(sessionId)
        │  ONE transaction; service-role only
        ▼
attempts + text_completions + profiles + streak, session sealed
        │
        ▼
test_sessions (completed) — immutable; /learn/[textId]/results/[sessionId] reads it
```

**The client never decides the test.** It sends a text id and gets back a session.
It cannot drop the hard questions, repeat an easy one, or mix in items from another
passage.

**Every answer is written at most once.** The primary key `(session_id, question_id)`
plus an update guarded on `answered_at is null` make that a database guarantee, not
a React one — so a double tap, an offline retry or a replayed Server Action re-reads
the stored answer instead of changing the score.

**Finalization is atomic and idempotent.** `finalize_test_session` locks the session,
recounts the score from the stored items, and writes attempts, the completion, the
profile, the streak and the session row together. Any failure rolls all of it back;
a second call writes nothing and returns the stored result. Refreshing the results
page, submitting twice, or two tabs racing all score the test exactly once.

**Resume works because the session exists.** Closing the tab mid-test and coming
back re-enters the same session at the first unanswered question. Finishing one and
starting again is a retake: a new session, a new Elo step, an overwritten completion.

### How correct answers are protected

`correct_idx` lives in `questions`, which learners have no `SELECT` on at all — they
read the answer-free `questions_public` view. The key is revealed in exactly one
place, `answer_test_question`, and only when all of the following hold: the question
belongs to the caller's own session, that session is `in_progress`, and the caller's
single answer for that question has just been committed. Learning the key therefore
costs the attempt it belongs to.

The placement test works the same way, and goes one step further: its result is
**replayed** from the answers stored in `calibration_session_items`, not reported by
the browser. `finalizeCalibrationSession` takes only a session id and recomputes the
rating with the same `updateAbility` the on-screen estimate used, so the learner sees
the level they watched being built while a forged one has nowhere to enter.

### Who may write what

| Learner may edit | Server-owned — written only by the learning engine |
| ---------------- | -------------------------------------------------- |
| `profiles.display_name`, `profiles.daily_word_goal` | `profiles.ability`, `rd`, `answered`, `cefr_estimate`, `promotion_streak`, `level_source`, `streak_days`, `last_active`, `words_reviewed_today`, `word_streak_days`, `last_word_review` |
| `saved_words` (their own review deck) | `attempts`, `text_completions`, `test_sessions`, `test_session_items`, `calibration_sessions`, `calibration_session_items` — readable by their owner, writable by nobody else |

Three mechanisms enforce this, not one: the progress tables have **no insert/update
RLS policy** at all; a `BEFORE UPDATE` trigger on `profiles` rejects a browser write
to any server-owned column (while leaving the two editable ones alone); and the
finalize functions have `EXECUTE` **revoked from `anon` and `authenticated`**, so
the computed rating can only arrive from server code holding the service-role key.

`profiles.level_source` records where a level came from — `manual` (self-declared in
settings: clamped, `rd` reset to full uncertainty, `answered` untouched), `placement`
(a replayed placement test) or `test` (earned by finishing reading tests). Choosing
your own level is still a supported, deliberate choice; it is simply never mistaken
for a level you proved.

Design rationale and the alternatives considered are in
[`docs/architecture/test-sessions.md`](./docs/architecture/test-sessions.md).

## Learning engine

An Elo rating says *how well* a learner is doing. It cannot say **what they
know** — whether they recognise a word but could never produce it, whether they
keep losing Dativ after prepositions, or how long ago any of it was last true.
The learning engine records that, in two layers kept strictly apart:

- **Evidence** (`learning_events`, `review_events`) — append-only, one row per
  interaction, never rewritten. This is what a better memory model can be fitted
  to later; if all we stored was `interval = 21`, that decision would be blind.
- **Knowledge** (`user_skill_state`, `user_concept_state`,
  `user_word_knowledge`) — a small aggregate the app can read on every render
  without touching a history that grows without bound.

Four things it deliberately refuses to do:

1. **Claim knowledge it has no evidence for.** Eight skills are catalogued;
   exactly three are measured today (reading comprehension, receptive vocabulary,
   grammar). Speaking is `unknown`, not a level inferred from reading.
2. **Turn recognition into production.** Recognising *Schwert* on a flashcard —
   however confidently graded — feeds only the **receptive** channel. The
   **active** channel stays untouched until an exercise actually asks the learner
   to produce the word. (None does yet, so active vocabulary reads as unknown.)
3. **Invent a weakness.** A wrong answer counts against the concepts its item is
   *tagged* with, and nothing else. And one mistake is never a weakness: a
   concept needs repeated, well-evidenced failures before it can be ranked.
4. **Let one answer look like proof.** Each state carries a `score` *and* a
   separate `confidence`; below a floor the model reports "za mało danych"
   instead of a level. The scores are an internal heuristic (`knowledge_v1`) and
   are **not** CEFR — the Elo rating remains the only thing that claims a level.

Evidence can only be created by the engine: no learner-writable path exists to
any of these tables, `apply_review` is service-role only, and
`apply_learning_evidence` is revoked from every role. One interaction is one
transaction, and one deterministic `event_key` per interaction means a double tap
or a retried request settles the same review rather than a second one.

Full rationale — the V1 algorithm, the evidence weights, the receptive/active
split, idempotency, and what could and could not be backfilled — is in
[`docs/architecture/learning-engine.md`](./docs/architecture/learning-engine.md).

## How the Level System Works

Each learner has an **ability** (Elo-style rating, starting ≈1200) and a **rating
deviation** `rd` (uncertainty, starting ≈350). Every question carries its own Elo
`difficulty`.

- **Expected score** — the probability a learner answers an item correctly is the
  standard Elo logistic: `1 / (1 + 10^((difficulty − ability) / 400))`.
- **Update** — after each answer the ability moves toward the surprise of the result:
  `ability += k · (actual − expected)`, where `actual` is 1 (correct) or 0 (wrong).
- **Adaptive step size** — the K-factor is derived from `rd` (`rd / 8`), so early
  answers (high uncertainty) move the rating a lot and later answers move it little.
  `rd` shrinks as more questions are answered, making the estimate progressively
  stable; the more surprising the result, the less it shrinks.
- **Confidence** — labelled from answer volume: *kalibracja* (<5), *niska* (<15),
  *średnia* (<40), *wysoka* (≥40).

The ability maps onto a **CEFR band** (`src/lib/cefr.ts`):

| CEFR | Elo range  |
| ---- | ---------- |
| A1   | `< 1150`   |
| A1+  | `1150–1300`|
| A2   | `1300–1450`|
| B1   | `1450–1600`|
| B2   | `≥ 1600`   |

The algorithms are pure functions in `src/lib/elo.ts` (ability), `src/lib/sm2.ts`
(SM-2 scheduling), and `src/lib/cefr.ts` (Elo ↔ CEFR), each with colocated Vitest tests.

## Architecture notes

- **`src/proxy.ts`** — Next.js 16 renamed the `middleware` convention to `proxy`. It
  refreshes the Supabase session on every request via `lib/supabase/middleware.ts → updateSession()`.
- **`src/actions/{start,answer,finalize}-test-session.ts`** — the test lifecycle.
  Sessions are server-owned: the server decides which questions count, each answer is
  written exactly once, and finalization is a single atomic transaction. See
  [Test session lifecycle](#test-session-lifecycle).
- **`src/lib/supabase/service.ts`** — the service-role client. It exists so that
  finalizing a test is reachable from trusted server code and *only* from there;
  `finalize_test_session` has `EXECUTE` revoked from `anon`/`authenticated`.
- **`src/lib/errors.ts`** — the error taxonomy for those flows. Expected failures are
  returned, not thrown (Next redacts thrown Server Action errors in production);
  technical detail is logged server-side and the learner sees one Polish sentence.
- **`src/actions/update-srs.ts`** — grades one review card. A single atomic call
  writes the `review_events` row (SM-2 state before → after), moves the schedule,
  advances the daily counter and records the learning evidence; an
  `interactionId` minted per card makes a double tap settle the same review.
- **`src/lib/learning/`** — the knowledge domain, all pure and unit-tested:
  `skills.ts` / `concepts.ts` (the catalogs), `evidence.ts` (what each interaction
  proves, and what it is worth), `knowledge-model.ts` (the V1 score/confidence
  algorithm), `aggregate.ts` (folding evidence into state), `queries.ts` (the
  read layer — `getUserSkillProfile`, `getUserWeakestConcepts`,
  `getUserWordKnowledge`). The arithmetic never touches Supabase; the database
  owns transactions, `src/lib/` owns the maths.
- Server data is fetched through TanStack Query hooks in `src/hooks/`; client-only
  ability state lives in the Zustand store `useAbility`.

## Legal Note

DTZ wordlist headwords (lemmas, articles, grammatical information) are factual
linguistic data. All Polish translations, example sentences, and reading texts in this
app are independently generated. Correct answers to comprehension questions are never
exposed to the client — a question's key is readable only inside `answer_test_question`,
and only for a question in the caller's own in-progress test session, after their answer
to it has been committed.
